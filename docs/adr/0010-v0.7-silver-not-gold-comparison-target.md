# ADR-0010: v0.7's DLT comparison target is Silver, not Gold

**Status:** Accepted
**Date:** 2026-07-27
**Related:** [ADR-0002](0002-use-dbt-for-silver-gold.md), [ADR-0009](0009-agentic-integration-mcp-gated-review-then-act.md)

## Context

ADR-0002 deferred Lakeflow Declarative Pipelines (DLT) to `v0.7` with a specific
scope: *"re-implement part of Gold with Declarative Pipelines once the dbt
approach is understood, and compare the two directly."* Planning `v0.7`'s
implementation surfaced a problem with that literal scope: Gold in this project
is mostly plain `GROUP BY` aggregation SQL (see `src/dbt/models/gold/metrics/`).
A DLT materialized view re-implementing the same aggregation looks nearly
identical to the existing dbt model — same `SELECT ... GROUP BY`, no
expectations to speak of, no meaningful streaming-vs-batch question. It would
satisfy ADR-0002's literal wording while producing almost nothing substantive
to compare or write about, undermining the "Declarative ETL, DQ-as-code, vs.
dbt" learning goal ADR-0002 itself named as the point of keeping DLT in scope
at all.

The comparison is genuinely substantive one layer down, in Silver:
`stg_raw_events → int_events_deduped` (generic dedup + envelope-timestamp/
source-struct drift resolution) `→ int_transactions` (payload drift
resolution: `risk` struct-vs-string, `amount_minor` int-vs-string, currency/
country cleaning) `→ int_transactions_clean`/`int_transactions_dlq` (the
clean/DLQ split). This is the exact `transaction.*`/ndjson slice
`docs/02-silver.md` names as the original proof-of-concept before Silver's
full build — self-contained, and its output already feeds
`gold.fct_transactions`, giving a known-good downstream to cross-check DLT's
output against without needing to also rebuild Gold in DLT.

## Decision

`v0.7`'s DLT re-implementation targets **Silver**, specifically the four-model
`transaction.*`/ndjson slice above, not Gold. Output lands in parallel schemas
(`novalake.bronze_dlt`, `novalake.silver_dlt`), never overwriting the existing
dbt-built `bronze`/`silver`/`gold` tables. `gold.fct_transactions` is read
read-only as a downstream cross-check that the DLT Silver output is correct,
not rebuilt. This is a genuine deviation from ADR-0002's literal wording, not
a reinterpretation of it — recorded here per this project's ADR convention
(status change via a note on ADR-0002, not a silent edit) rather than folded
silently into the `v0.7` phase doc.

## Consequences

- ADR-0002 gets a `Status` note pointing here; its Context/Decision/
  Consequences/Alternatives content otherwise remains accurate history.
- `v0.7`'s deliverable is 4 DLT SQL files (`pipelines/transformations/bronze/
  raw_events.sql`, `pipelines/transformations/silver/{events_deduped,
  transactions,transactions_clean,transactions_dlq}.sql`) mapped 1:1 to 4 dbt
  models, not a DLT Gold layer.
- The comparison write-up (`docs/07-declarative-pipelines.md`) can report on
  dedup semantics (streaming-table `ROW_NUMBER` vs. dbt's full-table
  recompute), DLQ inspectability (`EXPECT ... DROP ROW` vs. dbt's `_clean`/
  `_dlq` pair), and payload-drift-resolution parity — all genuinely comparable
  logic — instead of a near-identical `GROUP BY` translation.
- No DLT Gold layer exists after `v0.7`; if a future phase wants one, that is
  its own scope decision, not implied by this one.
- `gold.fct_transactions` is the validation anchor for `v0.7`'s Silver output
  (row-count and column-content cross-checks), so `v0.7` has an implicit soft
  dependency on Gold's existing correctness — acceptable since Gold is stable,
  tagged, and unrelated to the DLT build itself.

## Alternatives considered

- **Build the originally-scoped Gold materialized view anyway, to satisfy
  ADR-0002's literal wording.** Rejected — produces a near-identical
  translation of existing `GROUP BY` SQL with little to compare, undermining
  the learning goal ADR-0002 itself named as the reason to keep DLT in scope.
- **Build both a Gold DLT layer and the Silver slice above.** Rejected — real
  scope growth (a fifth/sixth DLT file, a second target schema layer, extra
  validation surface) for a Gold comparison already judged low-value; the
  Silver slice alone delivers the comparative learning goal.
- **Silently redefine `v0.7`'s scope in the phase doc without a formal
  record.** Rejected — this project's own convention (`docs/adr/README.md`:
  "corrections get a new ADR, not a silent edit to an old one") exists
  specifically to prevent decisions like this from becoming undocumented
  drift between what ADR-0002 says and what actually got built.
